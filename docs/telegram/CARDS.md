# Карточки-картинки для сообщений бота (TG20 / TG15)

Статус: **решено владельцем (30.10.2026): путь а1, `@resvg/resvg-js` на сервере, макет A, шрифт Inter,
12 мотивирующих фраз по кругу, на карточке рекорд этой тренировки.** Реализовано в `api/telegram-card.mjs`
(см. раздел «Как это сделано» в конце). Ниже сравнение, на основании которого принято решение.
Текстовые сообщения при этом уже исправлены (русский язык по умолчанию, склонения): они остаются
запасным вариантом и подписью под будущей картинкой.

## Что нужно получить

PNG 1080×1080 (макеты `designs/workout-reports-20261022`, направления A/B/C): название тренировки,
фигурка спереди и сзади с подсвеченными мышцами, группы мышц, длительность, тоннаж, подходы/повторения,
итоговая фраза. Для недельного итога то же по неделе. Отправка через Bot API `sendPhoto`
(multipart, `caption` не длиннее 1024 символов).

Два разных момента отправки, и это главное для выбора способа:

| Сообщение | Кто запускает | Есть ли открытое приложение |
|---|---|---|
| Итог тренировки | `maybeNotifyNewWorkout` при `PUT /api/data` | **Да**, тренировку только что сохранил клиент |
| Недельный итог | `telegramWeeklyTick` по таймеру, понедельник после 09:00 | **Нет**, приложение никто не открывал |

Клиентский рендер может закрыть только первое. Для второго картинку должен рисовать сервер.

## Что можно брать как исходник (лицензии)

- **Каталог упражнений (`catalogue/media`) нельзя**: лицензия Gym visual, любые картинки и анимации
  запрещены вне приложения и не отдаются AI-инструментам.
- **Схема тела** (`frontend/src/lib/body-paths.js`: муж./жен. × спереди/сзади, около 90 КБ) производная
  от MuscleMap (Melih Colpan, **MIT**), это уже указано в `NOTICE.md`. Использовать можно при условии
  сохранения уведомления MIT. Это не медиа каталога. Макеты в `designs/` построены на тех же контурах
  (`body-geometry.json`, 520 КБ, с подчастями; для карточки брать компактную версию из `body-paths.js`).
- Данные для подсветки: `lib/muscles.js` (`MUSCLES`, `INERT`, `levelsOf`, `loadOfWorkouts`) и
  `muscleSnapshot.muscleWeights` в самой тренировке (их уже читает `statsForWorkout` на сервере).
- Шрифт картинки: нужна лицензия, допускающая встраивание (SIL OFL: Inter, Roboto, Noto Sans, PT Sans
  с кириллицей). Какой шрифт в макетах, проверить отдельно.

## Способы

### (а) Сервер: SVG в PNG

Сервер собирает SVG строкой из данных тренировки (контуры из `body-paths.js`, текст, цвета) и
растеризует.

**а1. `@resvg/resvg-js`** (Rust, N-API, готовые бинарники для `linux-x64-musl` и `linux-arm64-musl`).
- Плюсы: один пакет, быстро; шрифты передаются в вызов (`fontFiles`/`fontBuffers`), **системные шрифты
  и fontconfig не нужны**; результат одинаков везде; JS-зависимостей нет; память на один рендер 1080²
  порядка десятков МБ и только на время рендера.
- Минусы: **ещё одна, нативная зависимость в `api/`** (сейчас три), порядка единиц МБ в образе, шрифты
  (сотни КБ) кладутся в репозиторий, за бинарником надо следить (обновления, уязвимости).
- Риски: платформенный бинарник приходит как optional-зависимость, а наш Dockerfile ставит
  `npm ci --omit=optional`, поэтому **Dockerfile придётся менять**; проверить, что на сервере выбран
  musl-вариант нужной архитектуры. Размеры и память указаны ориентиром, сборку образа я не делал.

**а2. `sharp`** (libvips + librsvg). Самый распространённый, но тяжелее (десятки МБ бинарников), текст
идёт через librsvg и fontconfig, то есть в Alpine нужны системные шрифты (`apk add`). Те же
optional-зависимости. Для одной карточки избыточно.

**а3. Без зависимостей** (свой растеризатор и PNG-кодек на `zlib`). Контуры тела это кривые Безье, а
текст со шрифтом без библиотеки не нарисовать. **Не рекомендую.**

### (б) Клиент: Canvas, PNG, сервер, `sendPhoto`

В `frontend/src/lib/workout-card.js` уже есть карточка («Поделиться картинкой»: `workoutCardModel`,
`layoutWorkoutCard`, `drawWorkoutCard`). После сохранения тренировки клиент рисует её на Canvas,
получает `toBlob('image/png')` и шлёт на новый маршрут (например, `POST /api/telegram/card`); сервер
пересылает файл в `sendPhoto`.

- Плюсы: **ни одной новой зависимости**, образ и память сервера не меняются, шрифты и рисование уже
  решены и протестированы, схема тела уже в приложении.
- Минусы и риски:
  1. **Недельный итог невозможен** (нет открытого клиента), остаётся текстом.
  2. Новая точка приёма картинки от клиента: нужны жёсткие проверки (размер до ~500 КБ, сигнатура PNG и
     размеры, один запрос на тренировку, получатель только `telegramId` из сессии, а не из тела), иначе
     через неё можно слать произвольные картинки в свой чат и создавать нагрузку.
  3. Рисует устройство: шрифты и вид могут отличаться между Android и iOS WebView.
  4. Доставка зависит от клиента: закрыл приложение сразу после «Завершить», картинка не уйдёт.
     Нужен запасной текст: сервер ждёт картинку N секунд, иначе шлёт текст.
  5. Содержимое картинки сервер не проверяет (подделка цифр попадёт только в чат самого пользователя,
     риск низкий).

### (в) Отдельный контейнер рендера

Chromium/Puppeteer для этого неприемлем (сотни МБ RAM и образа на сервере с 1 ГБ). Node+resvg в отдельном
контейнере даёт те же +1 зависимость и ещё образ, сеть, healthcheck, деплой. Выгоды против (а1) нет,
расходов много. **Не рекомендую.**

## Сравнение

| Критерий | (а1) resvg на сервере | (б) Canvas в клиенте | (в) отдельный контейнер |
|---|---|---|---|
| Новая зависимость | да, 1 нативная | нет | да, плюс образ |
| Меняет Dockerfile `api` | да | нет | новый Dockerfile |
| Недельный итог | да | нет | да |
| Память сервера | кратковременно десятки МБ | 0 | постоянный процесс |
| Одинаковый вид у всех | да | зависит от устройства | да |
| Новая поверхность атаки | нативный бинарник | приём картинки от клиента | сеть между контейнерами |
| Повторное использование | контуры из `body-paths.js`, новый SVG-шаблон | `workout-card.js` как есть | как (а) |
| Объём работы | средний | малый | большой |

## Рекомендация

1. **Целевой путь (а1): resvg-js на сервере.** Только он закрывает оба сообщения (тренировка и неделя),
   даёт одинаковый вид и не требует открытого приложения. Цена: одна нативная зависимость и правка
   Dockerfile; шрифты и контуры лежат в репозитории.
2. **Если зависимость недопустима: (б) только для итога тренировки**; неделя остаётся текстом.
3. (в) не делать.

Безопасность серверного рендера: на вход только числа и наши подписи мышц (из `MUSCLE_NAMES`), название
тренировки через `cleanText` и экранирование XML; пользовательский SVG не принимать; во вставляемом SVG
нет внешних ссылок. Один рендер за раз (очередь) и таймаут. При любой ошибке уходит прежний текст через
`sendMessage`; под картинкой короткая подпись (название и цифры).

## План реализации (а1), когда решение принято

- `api/card-svg.mjs`: чистая функция `workoutCardSvg(stats, lang)`; тесты структуры и экранирования.
- `api/body-paths.mjs`: копия контуров для API (образ API не импортирует фронтенд; по образцу «Code that
  exists twice on purpose» из `CLAUDE.md`, с тестом паритета с `frontend/src/lib/body-paths.js`).
- `api/card-render.mjs`: ленивый `import('@resvg/resvg-js')`; без пакета возвращает `null`, работает
  текст, как сейчас.
- `sendTelegramPhoto(chatId, png, caption)`: multipart через `FormData` и `Blob`, без зависимостей.
- Тесты: PNG с верной сигнатурой и размером 1080×1080, цвета мышц по нагрузке, откат на текст при ошибке.

## Как это сделано

- `api/telegram-card.mjs`: `cardModel` (что на карточке), `workoutCardSvg` (SVG, все строки экранируются),
  `renderCardPng` (resvg загружается лениво; при ошибке возвращает `null`).
- Рекорд тренировки: самый тяжёлый выполненный рабочий подход (при равенстве больше повторений); разминки
  и неотмеченные подходы не считаются; название берётся из `api/card-assets/exercise-names.json`
  (генерируется `node scripts/catalogue/build-card-names.mjs`, только текст) или из `customEx` профиля.
- 12 фраз на язык (`PHRASES`), выбор по кругу: счётчик `cardPhraseIdx` у пользователя, шаг на каждый отчёт.
  Фразы нейтральные по роду, потому что Telegram не сообщает пол.
- Контуры тела: `api/card-assets/body-male.json` (MuscleMap, MIT), тест сверяет с `frontend/src/lib/body-paths.js`.
  Шрифт Inter (OFL) лежит в `api/card-assets/`, указан в `NOTICE.md`. Системные шрифты не нужны.
- Отправка: `sendPhoto` (multipart), подпись из первых трёх строк текстового сообщения. Если рендер или
  Telegram не удались, уходит прежнее текстовое сообщение. `TELEGRAM_CARDS=0` отключает карточки.
- Dockerfile: `npm ci --omit=optional` пропускает нативный пакет, поэтому отдельным шагом ставится
  `@resvg/resvg-js-linux-<arch>-musl` той же версии. Без него сервер работает, карточка заменяется текстом.
- Недельный итог пока остаётся текстом (отдельная карточка недели, макет A-week, не делалась).

## Не проверено

Сборка Docker-образа (демон Docker был недоступен), реальная отправка `sendPhoto` и вид в Telegram.
Проверено: тесты, рендер PNG 1080×1080 на Windows с тем же пакетом (проверка на musl только через образ).
